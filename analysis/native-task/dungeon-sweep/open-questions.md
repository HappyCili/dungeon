# 未决问题

## 1. 协议与状态

1. **`Dun_sweep ret=4` 的含义**：日志只证明错误码稳定出现，原生代码只拼接 `notice.dungeon.sweepRet4`；需要原生语言表、服务端错误码表或带 UI 文案的运行时样本。
2. **`compeleted` 是否是服务端扫荡硬前置**：原生按钮明确依赖它，但当前 Python `DungeonStatus` 没有投影 field 11。应补充解码和测试，避免把“可见/已解锁”误当成“已通关可扫荡”。
3. **`treasuryTimes` 与 `drawtimes/totaltimes` 的关系**：原生同时维护两套字段；当前实现只用全局累计次数，尚未证明按地下城的 `treasuryTimes` 可以被忽略。
4. **`Dun_point_update_notify` 的时序**：处理器会更新 `totaltimes`，但现有 832 条地下城日志没有 19618；需要一次包含扫荡后状态推送的短窗口采集。
5. **宝库信息面板的后续发送**：主 JS 只留下 `Dun_treasure_info` 的入口和 `DungeonTreasurePanel2/3` 的打开动作；当前 `PlayerAssets` Bundle 没有可读 TextAsset，不能静态确认面板是否总是发送 `all=true`、是否支持单抽。

## 2. 日常奖励

1. **任务 107 的直接积分领取**：可识别的日常状态出现过 `finished=true`，但现有 19702 出站样本只包含 101、102、103、201。需要在任务 107 刚完成的窗口保存完整帧序列。
2. **日常重置边界**：`dailylt/dailyrt` 只表示剩余/重置倒计时，当前资料未确认服务器时区和跨日行为。
3. **多条件任务进度**：`daily_quest.py` 只在条件 ID 与任务 ID 相同时记录进度；若任务 50601 的配置在其它版本变为多条件，需要重新核对。
4. **领取响应的聚合形式**：`19702`/`19704` 支持 `ids[]`/`rewardids[]` 聚合回包，日志中有一条无对应单项请求的聚合响应；需要确认这是服务端批量推送还是日志窗口边界造成的残留帧。
